# Commands Reference

This file is the on-demand command surface reference. The session bootstrap (`framework/concepts.md`) owns trigger routing (trigger → first action → command package files); this file documents what each command does and who calls it, plus target resolution. Phase execution protocols are owned by the command package files the bootstrap names (checklists, workflows, operation procedures).

## Target Resolution

`validate`, `revalidate`, and `promote` accept either a unit or a rule. `verify` and `reverify` are unit-only; a rule uses validate as its sole quality gate. Resolve `validate`, `revalidate`, and `promote` with this three-stage process. Resolve `fresh@{target}` with the separate existing-target process below.

The read-only command `specflowctl resolve --target <name>` executes the three-stage resolution mechanically: it prints the resulting type (`unit`, `rule`, `ambiguous`, or `not_found`), the full `rule_id` for a rule, and every matched path. The stages below are its specification; on `ambiguous`, list the matched paths and ask the user to choose; never pick one.

**Stage 1 — Physical file check.** Inspect both layers for every exact possibility before deciding:

- When `{target}` has no rule prefix: `docs/specs/units/{candidate,stable}/unit_{target}.md`, `docs/specs/rules/{candidate,stable}/g_rule_{target}.md`, and `docs/specs/rules/{candidate,stable}/b_rule_{target}.md`.
- When `{target}` starts with `g_rule_` or `b_rule_`: `docs/specs/rules/{candidate,stable}/{target}.md` — the target text is already the full rule id, so appending a prefix again would name no real file.

The same logical object in both layers is one match. Treat a unit name and a rule ID as different objects even when the target text is the same.

**Decision (use after all possibilities above have been inspected):**

| Distinct objects matched | Result |
|---|---|
| Exactly one | Use its type: Unit, or Rule with the full `rule_id` from the matched filename (e.g., `b_rule_runtime_model.md` → `rule_id = b_rule_runtime_model`). |
| Two or more | Ambiguous. List every matching path and ask the user to choose; never pick one. |
| None | → Stage 2 |

**Stage 2 — Prefix fallback (new target).** Only reach here if no file was found in Stage 1:

| Target format | Detected as | Example |
|---------------|-------------|---------|
| Name without prefix (`auth`, `user_service`) | Unit | `validate@auth` |
| Name with `g_rule_` or `b_rule_` prefix | Rule | `validate@b_rule_auth` |

**Stage 3 — Rule directory fallback.** Only reach here when Stage 2 detected "Unit" but no unit files exist for the target in either layer.

Run `Glob "docs/specs/rules/candidate/*.md"` and `Glob "docs/specs/rules/stable/*.md"`. Scan all filenames for one whose name contains the target (e.g., `b_rule_runtime_model.md` contains `runtime_model`). Ambiguity is between distinct rule ids; as in Stage 1, one logical rule found in both layers counts as one match, not two.

| Result | Action |
|---|---|
| Exactly one matching rule id | Type = Rule. Resolve the full `rule_id` from the matched filename and proceed with the rule pipeline. |
| Two or more matching rule ids | Ambiguous. List every matching path and ask the user to choose; never pick one. |
| No matching rule file | Report: target does not exist. |

### Existing-Target Resolution for `fresh@{target}`

`fresh` reports an existing object; it never classifies or creates a new target. Before invoking the CLI, inspect both candidate and stable layers for every exact possibility:

- Unit: `docs/specs/units/{candidate,stable}/unit_{target}.md`.
- Rule when `{target}` starts with `g_rule_` or `b_rule_`: `docs/specs/rules/{candidate,stable}/{target}.md`.
- Rule when `{target}` has no rule prefix: both `docs/specs/rules/{candidate,stable}/g_rule_{target}.md` and `docs/specs/rules/{candidate,stable}/b_rule_{target}.md`.

Treat the same unit or full rule ID found in both layers as one logical match. Then act on the complete result:

| Matches | Action |
|---|---|
| One unit, no rule | Run `specflowctl fresh --unit {target}`. |
| No unit, one full rule ID | Run `specflowctl fresh --rule {rule_id}`. |
| A unit and any rule, or multiple full rule IDs | Ambiguous. List every matching path and ask the user to choose. |
| None | Report that the target does not exist. |

Never run bare `specflowctl fresh` for `fresh@{target}`. Without `--unit` or `--rule`, the CLI produces a scope summary rather than target detail.

The applicable path depends on the target:

| Step | Unit | Rule |
|---|---|---|
| validate | 10-point unit design checklist (`unit_validate_checklist.md`) | Rule metadata and body-quality checklist (`rule_validate_checklist.md`) |
| verify | Required: spec-vs-code check (`unit_verify_checklist.md`), run as one gate with two lenses — `alignment` and `quality`. The alignment lens runs in item sessions (Steps 2, 3, 4, and 6 per acceptance item, with Step 7 for the mismatches they raise) and one unit-level scan session per run (`unit:<unit>`, Steps 1 and 5, with Step 7 for its own mismatches) | Not applicable; rule verify was removed |
| promote | candidate→stable archive (`unit_promote_workflow.md`) | version promotion + consumer migration (`rule_promote_workflow.md`) |

## Command Reference

| Command | What it does | Who calls it |
|---------|-------------|-------------|
| `specflowctl fork --unit <name>` | Copy stable unit spec + appendices to candidate layer (pure copy, layer encoded by path), inherit pass stable confirmation caches into the candidate round (rewritten to the candidate layer; gates without a usable baseline are listed in the manifest), and copy the stable promise state to candidate. Rejects if candidate already exists or stable does not exist. | Agent (as fork prerequisite) |
| `specflowctl fork --rule <id>` | Copy stable rule to candidate layer (pure copy, layer encoded by path). Rejects if candidate already exists or stable does not exist. | Agent (as fork prerequisite) |
| `specflowctl next --unit <name>` | Discover unit files, dependencies, and the promise model. Reports each promise and its `depends_on`; reports `Promise model: INVALID — ...` when the spec has no `## Promises` section or the section is malformed. When neither a candidate nor a stable spec exists for the unit, reports the empty state (no design recorded) with exit code 0; fails on tool errors. | Agent |
| `specflowctl promote --unit <name>` | First checks direct rule publication: missing stable explicit refs or different bound candidate/stable content block; pending global drafts are advisory. Runs the promise checks (a unit without `## Promises` is rejected), requires `promise_state_candidate.yaml`, validates that the state's own promises and dependency pins are current, and requires every pinned provider promise to exist in the stable layer at the same fingerprint (missing state rejects with guidance to run verify; an unpublished provider rejects with guidance to promote the provider first). Then checks the merged validate+verify (+appendix) cache freshness, validates format + copies candidate→stable, rewrites the candidate gate caches and stages the stable promise state in the same publication transaction (`target: stable`, paths rewritten to `stable/`). The verify cache must carry both the `alignment` and `quality` sections (both lenses) and be fresh, `mode: full`, non-blocking. Rejects if any cache stale, missing, or blocking. Also rejects if any appendix file is missing from the validate cache. | Agent (after user confirmation, after validate+verify) |
| `specflowctl promote --rule <id>` | Checks rule validate cache freshness, validates rule frontmatter, copies candidate rule→stable, deletes candidate, rewrites the rule validate cache into a stable confirmation cache. Rejects if the cache is missing or stale. Consumer impact assessment is the agent's responsibility. See `framework/spec_writing_guide.md` §6. | Agent or human maintainer |
| `specflowctl review run-*` | Governance review run-state management. Subcommands: `collect-default-scope` (collect the deterministic default scope for a review flow), `run-init` (create/reuse run-state), `run-validate` (validate run-state shape), `run-refresh` (recompute fingerprints, mark stale), `run-touch` (update timestamp). See `framework/spec_flow_review.md` §6. | Deep audit executor |
| `specflowctl operation ...` | Operation-scope state carrier. `open` declares and freezes a bounded change scope (target spec-derived surface + explicit `--allow` paths + `--require-spec` paths) and records the starting commit plus the working-tree snapshot every later check measures against; `check` mechanically evaluates the final change set against it (read-only, fail closed); `close` ends the operation (it removes the state; a normal close requires PASS, and `--abandon` ends a violating operation explicitly, removing the state with the `abandoned` outcome printed); `update` widens the declared scope explicitly (user-authorized only); `status` inspects open operations. State: `meta/operations/<id>.json` (local process state; removed by `close`, and a surviving closed state is swept by `specflowctl clean`). See `framework/operations/operation_scope.md` and `tooling/README.md` §Operation scope. | Agent (when the project rules or the user require bounded scope) |
| `validate@{target}` (agent trigger) | Complete runs fix a coverage set (the validate check groups) and write through `gate-finalize`; a candidate full FAIL writes the failure record (`revalidate@{target}` is the recovery). Targeted checks execute directly and never publish a complete cache. A targeted P0/P1 must immediately run `gate-invalidate --gate validate ... --check {key}` so a pass cache is deleted or a failure-record invalidation is persisted. | User says "validate" or confirms agent suggestion |
| `verify@{target}` (agent trigger) | Complete unit runs fix a merged coverage set (alignment = the acceptance item tasks plus the always-present `unit:<unit>` unit-level scan of Steps 1 and 5; quality = public code, unit design and unit architecture tasks) and write through `gate-finalize`; rule verify has been removed. Complete FAIL writes the failure record. Targeted checks never publish a complete cache; targeted P0/P1 immediately runs `gate-invalidate --gate verify ... --check {item}`. | User says "verify" or confirms agent suggestion |
| `revalidate@{target}` (agent trigger) | Change-review delta/repair coverage run. The review session accepts, names re-run keys, or escalates to full; failed checks, persisted `invalidated_checks`, current checks the baseline never declared, and explicit `--rerun` overrides are forced mechanically; unmappable failed or invalidated keys get a full-scope plan (which re-runs the standing relationships). Writes `basis: delta|repair` with the recorded review; FAIL updates the failure record. | User says "revalidate" or confirms agent suggestion |
| `reverify@{unit}` (agent trigger) | Mechanical verify delta/repair coverage run: `gate-plan` derives the re-run set from each conclusion's own judgment-record pins (changed file or region, moved protocol, invalidation, missing record) and from the evidence its key currently requires (a new file in a declared surface), plus current keys the baseline never declared and explicit `--rerun` overrides; repair also forces failed judgments, persisted invalidations, and failed relationships. No change review is scheduled. Writes `basis: delta|repair` with no review record; FAIL updates the failure record. | User says "reverify" or confirms agent suggestion |
| `promote@{target}` (agent trigger) | Resolves type through §Target Resolution, then uses the unit 3-step or rule 2-step workflow. Unit: archive (`unit_promote_workflow.md`). Rule: version promotion + consumer migration (`rule_promote_workflow.md`). On FAIL: rejects unpublished bound-rule content or invalid explicit rule refs before checking caches; also rejects if an applicable cache is stale/missing/blocking, the merged verify cache does not cover both lenses, format is invalid, or copy fails; changes no truth. Report the concrete blocker: an unpublished rule requires user-triggered rule promotion, while a gate gap requires its indicated user-triggered check before retrying. | User says "promote" or confirms agent suggestion |
| `specflowctl init` | Initialize specFlow project | Human |
| `specflowctl doctor` | Diagnose project setup | Human |
| `spec_flow_update` (agent trigger) | Full update: pull framework, detect format changes, migrate spec files, check document format. See `framework/operations/update.md` for full procedure. | User says `spec_flow_update` |
| `spec_flow_version` (agent trigger) | Check the installed SpecFlow version against the remote latest and report whether the project is up to date. If behind, recommend running `spec_flow_update`. See `framework/operations/version.md` for full procedure. | User says `spec_flow_version` |
| `specflowctl consumers --rule <id>` | List all units that reference the given rule in their rule_refs. For global rules (`g_rule_*`): returns every unit with a file in either layer — global rules apply to all units by default and are not repeated in rule_refs. For bound rules (`b_rule_*`): empty output means no consumers. Current-layer (effective) semantics: each unit resolves to its candidate file when one exists, falling back to the stable file (a stale stable file whose candidate dropped the reference no longer counts) | Agent for impact analysis |
| `specflowctl remove` | Delete explicitly selected units, rules, or appendices; repeatable mixed `--unit`, `--rule`, `--appendix UNIT:FILENAME.md`; `--layer all|candidate` (default all), optional `--dry-run`. Checks both remaining layers, cleans owned records, invalidates affected unfinished checks, sweeps the removed target's orphaned local run state and unreferenced shared task files, and verifies the transaction. See `framework/removal_workflow.md`. | Agent within authorized change scope |
| `specflowctl clean` | Remove disposable local state on demand: run directories whose target spec no longer exists or whose open state can no longer resume (a retired protocol or an invalid shape — never listed, never replaced by a replan, so the sweep is its only reclaim path — or planned evidence that can no longer resolve: a bound judgment or shared task record missing, unreadable, or no longer valid, the stale state `gate-status` exposes and no submission can repair; undecodable state and repairably damaged session state are never deleted), terminal run leftovers (a concluded run removes its own state; a surviving consumed or invalidated run is a crash leftover or pre-policy state), shared task files no surviving run references, the consumed scratch input manifests under `meta/plan_inputs/`, undeclared entries under `meta/` (strays — the framework-owned tree holds only the declared layout), and closed operation states under `meta/operations/` (a lifecycle that normally ends in the close command itself). `--dry-run` previews. The same sweep also runs automatically after `gate-plan` and after a successful `promote` or `remove`; `clean` adds the closed-operation sweep, whose normal end is the close command. It never touches committed caches, judgment records, review run-state, or lock files. See `framework/validation_cache.md` §Run lifecycle and `framework/verification_scope.md` §Input roles. | Agent or user when local state needs explicit cleanup |

| `specflowctl deps` | Read-only dependency analysis. `--scope all` (default, current-layer units — candidate preferred, stable fallback) / `candidate` / `stable`: reports the dependency graph from all in-scope units' promise `depends_on` edges; unit dependency cycle member lists are reported as INVALID (units mutually dependent through different promises — validate fails every unit on the cycle); the structural dependency order (dependencies first) is computed over every in-scope edge, so each displayed edge constrains the sequence; publication state is an edge annotation (`[wait]` — the provider contract is not yet published stable for a candidate consumer), not part of the structural ordering basis, and the `[wait]` edges are the only publication-order blockers (a unit dependency cycle separately fails validate and stops promotion); a publication-order cycle is the promotion diagnostic of a unit cycle whose edges are all unpublished (promise contract cycles are reported by validate Check 15); the promise edge report honors the selected scope. `--unit <name>`: the unit's promise provider refs, publication blockers, unit dependency cycle state, bound rules, promise consumers, and publication cycle state. `--rule <id>`: the units bound to the rule — explicit `rule_refs` consumers for a bound rule (`b_rule_*`), every current-layer unit for a global rule (`g_rule_*`, which applies by default and is not repeated in `rule_refs`); a global rule with no rule file is reported as not found. Pure mechanical computation — never infers dependencies from prose, never writes files. See `framework/verification_scope.md` §Dependency Analysis. | Agent on `deps@all` / `deps@{unit}` / `deps@{rule}` |
| `specflowctl surfaces` | Read-only view of code-surface associations and the immutable per-file judgments behind them. Derives current and stable associations from every in-scope unit's `implementation_surface` and `affects.files` (a directory declaration expands to its repository-content files; `implementation_surface` wins when both fields name the same file), reports the audited unit layers and the shared-file count, and prints per-file judgments — the valid public code records and each associated unit's design result, or `not checked or stale` when no valid current record exists; `--json` emits the audit report plus the judgment view. Sharing a file creates no behavioral dependency, an unfinished candidate never replaces a unit's stable requirements, and the command never writes. See `framework/shared_judgments.md` §File associations and `framework/spec_writing_guide.md` §14.4. | Agent when inspecting surface associations (`validate@{unit}` Check 9 evidence) |
| `specflowctl gate-plan` | Require the coordinator's `--relationships name[,name...]|none` for unit runs; union failed baseline relationships; for validate schedule a change review when unchanged passing relationship conclusions exist beside a non-empty change set (they carry mechanically when nothing changed), while a verify run re-runs them when any local conclusion re-runs or its pinned synthesis evidence changed, fix the immutable input snapshot and compute the **coverage set** (the judgment keys that must each receive exactly one verdict). The `--inputs-file` manifest adds evidence available to sessions but never creates a coverage key. Before a verify plan, discover related test and code-context paths for every item and list every discovered file in the input manifest, including files already in the declared surface — the manifest is readable background, and a newly supplied evidence input re-runs nothing, so `--rerun` is the way to force a re-check; this is path discovery, not a judgment. A verify plan's coverage set is the union of the `alignment` keys (the item keys plus the always-present unit-level scan key `unit:<unit>`) and the `quality` keys (public code, unit file design and unit architecture). Delta/repair runs snapshot carried judgments; verify delta scope comes from each conclusion's own record pins and the evidence its key currently requires, so a newly supplied evidence input re-runs nothing (a new declared-surface file does re-run the conclusions that require it), while a changed recorded file no conclusion pins is reported for full-run confirmation. `--format json` returns the run id, coverage set, carried keys, notices, the tooling's computed reviewer units (`reviewer_batches`) and the keys whose batch a session declared over capacity (`split_required_keys`) while the next action is `execute`, and the complete `deferred_findings` array for the coordinator (`[]` when none are pending). See `framework/verification_scope.md` §Coverage model. | Agent before executing any full/delta/repair quality-gate run that persists a cache |
| `specflowctl gate-extend` | Add supplementary evidence inputs to an OPEN gate run in place under the repository lock: files become snapshot refs, directories become expanded surfaces, logical references stay logical. The run id, coverage set, and every accepted session stay fixed — a supplement broadens what sessions may read, not what their plan required — so only uncovered keys re-run with the extended read refs. Use it when a reviewer reports `missing read ref`; a new `gate-plan` would replace the run instead. See `framework/verification_scope.md` §Verify evidence discovery before planning. | Agent on the reviewer's incomplete session report |
| `specflowctl gate-mission` | Materialize a read-only reviewer mission from persisted run state for one agent-joined key batch (same lens and kind; a verify quality batch may hold the code and design keys of several files; a session's key set is split only when a session declared itself over capacity): `--run RUN_ID --keys K1,K2 --format prompt` prints one session's text to send verbatim to an independent reviewer; `--format json` prints the same mission's structured inputs, dependencies, constraints, and report contract. `--run RUN_ID --final` builds the optional final synthesis instead (run only when relationships are assigned or the primary pass produced findings). A rejected session's new mission includes its latest rejection reason. Rejects a batch that mixes lenses or mixes kinds outside the verify quality code+design exception, and one that covers an already-covered key; `--final` is refused while any coverage key is still uncovered (the same closure `gate-finalize` enforces), so a synthesis mission never claims a readiness its run lacks. A public mission claims its batch under the repository lock; reviewers remain read-only. | Agent before launching each session executor, and to build the final synthesis |
| `specflowctl gate-status` | Read-only report of coverage progress. `--format json` returns the run's covered and uncovered keys per lens, session states, the next action, the computed reviewer units (`reviewer_batches`, one per report kind and lens, or per reviewed file for verify quality; the coordinator joins the units of one lens and kind), and the keys whose batch a session declared over capacity (`split_required_keys`); `--run RUN_ID` is the recovery point after interruption. The text `Next:` hint prints the same units as runnable `gate-mission` commands — the coordinator may join the units of one lens and kind into one session, which never widens the read surface; those over-capacity keys are reported as needing a split instead of re-missioning the same batch. Text format remains available for humans. | Agent after planning or submitting each session, and after an interruption |
| `specflowctl gate-submit` | Validate and record one reviewer session report plus its immutable parsed result. A session assigned a multi-key batch that returns the declared `Session over capacity:` line instead of a report is recorded as `over_capacity` (terminal, its keys left uncovered) so the coordinator splits that batch — it is not a defective report. A single-key batch is atomic and has no smaller batch, so the declaration is not available for it and its text is rejected as a defective report. Reports carry no dependency declarations; the assigned keys must belong to the run's coverage set and not already be covered by an accepted session. The final synthesis is submitted as `--session cross --keys cross` and must dispose every finding (including the unit's pending deferred findings), supply the relationship results and quality conclusions, and carry a validated ownership record for every finding it defers to another unit; the tooling derives every effective logical status from the dispositions and findings — the report carries no status lines. | Agent (coordinator) after each session report is produced |
| `specflowctl gate-finalize` | `--run RUN_ID` only (plus optional timestamp/repo root). Enforces mechanical **coverage closure** (every coverage key covered by exactly one accepted session, plus carried baseline judgments for delta/repair) and the snapshot-unchanged check, then derives result, blocking, P0–P3 counts, and failure statuses from the accepted synthesis; deferred findings are recorded for audit and routed through the ledger, not counted or blocked. A run with findings must carry an accepted final synthesis; a run with neither assigned relationships nor findings finalizes directly. The coordinator cannot supply judgment values. A candidate full-run FAIL writes a failure record for every gate (validate/verify: per-check `status` map); no full-run FAIL deletes a cache — the record is the failure-recovery baseline. Finalize also collects stale-protocol judgment records that no current cache binding, accepted pointer, or open run reaches — including through the record-reference chain — inside the same mutation lock, after cache publication and before the run is marked consumed, and reports the reclaimed count and size; same-protocol superseded records and records that cannot be read are retained. | Agent after every coverage key is covered (and the final synthesis is accepted when relationships are assigned or findings exist) |
| `specflowctl validate` | Validate candidate spec structure (15 checks, including the promise-model check), rule validation (5 mechanical checks), file write permissions, or the standalone promise format (`validate promise-model --unit <name> [--layer candidate\|stable]`: three-section shape, promise schema, coverage, and promise graph). A unit without `## Promises` fails. See `framework/core/promise_model.md`. | Human maintainer or agent |
| `specflowctl fresh` | Read-only cache freshness report. `--scope candidate` (default): summary for every unit/rule with a candidate file. `--scope stable`: drift state for every stable unit/rule and the global stable-unit done view. `--scope all`: both. Unit summaries include a `done:` column; `--unit <name>` detail reports promise closure and `done`. `READY FOR PROMOTE` requires the promise state record to be present, the contract closure `CLOSED`, and every pinned provider promise published in stable at the same fingerprint, in addition to the applicable gates and rule publication. `--rule <id>`: detail for one target. A STALE gate additionally prints its mechanically detected change report (the localized change set a validate delta review consumes; verify rechecks each conclusion's own recorded pins; a provider contract change appears as a `promise <id>` entry). An INVALID gate predates promise pinning: delta/repair cannot use it, only the full command recovers it. The re-run scope itself is decided by the delta/repair plan — validate through its change review, verify from the conclusion records. A unit with pending deferred findings shows their count and source. Never writes/deletes caches or baselines. See `framework/validation_cache.md` §Freshness Check. Candidate unit readiness also checks direct rule publication; missing stable explicit refs and differing bound content block, while global drafts are advisory. The publication check is read-only and separate from cache state. | Agent on `fresh@{target}` / `fresh@candidate` / `fresh@stable` / `fresh@all` |
| `specflowctl resolve` | Read-only three-stage target resolution (`framework/commands.md` §Target Resolution) for `validate`/`revalidate`/`promote`: `--target <name>` prints the classified type (`unit`, `rule`, `ambiguous`, or `not_found`), the full `rule_id` for a rule, and every matched path; a rule-prefixed target with no spec files is reported as a new rule target. Exits 0 on a single classification; exits 1 on `ambiguous` (every match listed — ask the user to choose) and on `not_found`. Never writes. | Agent as the first action of `validate@{target}`, `revalidate@{target}`, and `promote@{target}` |

Shared judgment invalidation: `specflowctl gate-invalidate --judgment <id> --reason <evidence>` preserves history and invalidates all dependent judgments. `surfaces` displays current/stable associations and per-unit judgments. See `framework/shared_judgments.md`.
