# Shared Verify Judgments

## Audience

This protocol runs in an installed consumer project. Framework development in the source repository does not require consumer unit declarations.

## File associations

`implementation_surface` and `affects.files` name files participating in a unit's implementation. A file, including a file expanded from a directory, may be associated with several units. File sharing alone creates neither a dependency nor a new unit. Units describe independent responsibilities; behavior, data meaning, and shared agreements still have one authoritative source. Shared constraints are published in rules rather than restated in several specs. An unfinished candidate does not replace that unit's stable requirements.

Reverse surplus checks read complete associated files, then compare only structures and designs belonging to the judgment's unit responsibility. Independent behavior outside that responsibility is not surplus merely because it is absent from this unit's spec. Attribute the boundary using implementation, callers and data flow; file association alone proves neither ownership nor exclusion. Helpers and shared mechanisms implementing or constraining the assigned requirement remain in scope. Missing attribution evidence requires adding the missing input to the open run with `specflowctl gate-extend` before judging surplus.

### Evidence-file roles and association display

`affects.evidence_files` names read-only verification evidence for the citing item: it joins the run snapshot and the item session's read refs, but it never becomes implementation participation, a quality coverage key, or operation write scope.

`specflowctl surfaces` derives current and stable associations from spec declarations and displays public code judgments and each unit's design judgments. The association view is not manually maintained review state.

## Required tasks

| Key | Lens | Responsibility |
| --- | --- | --- |
| `code:<file>` | quality | Collect code facts and potential problems independently of unit-private design |
| `design:<unit>:<file>` | quality | Actively check that unit's design requirements and decide each public observation |
| `architecture:<unit>` | quality | Assess all six Dimension 8 fields once for the entire unit |
| `item:<unit>:<item>` | alignment | Verify the current unit's acceptance requirement (Steps 2, 3, 4, and 6; Step 7 for the session's mismatches) |
| `unit:<unit>` | alignment | Scan the whole unit once: Step 1 structural alignment and Step 5 implementation integrity and surplus detection, plus Step 7 for the scan's mismatches; one session per run |

A public file's evidence surface is what the run declares and supplies: the reviewed file itself, its cited `affects.evidence_files`, the declared dependency spec objects and applicable rules, plus the related files the coordinator supplied through the input manifest. There is no repository-wide name- or stem-based discovery: a reviewer never links a file to another because their names share a stem or a token.

A public report must not suppress observations using private spec rationale. Reviewers must also find spec violations absent from the public observations: retention creates a finding for this unit, while suppression changes only this design judgment.

### Task batching and record inputs

Batches are computed, not chosen: the tooling partitions the uncovered coverage set into the run's reviewer units — one per report kind and lens, and, for the verify quality lens, one per reviewed file. The units are joined, not obeyed: the coordinator joins the units of one lens and kind into a session before missioning them, and splits a session's key set only when a session declares it exceeds that session's capacity (`framework/verification_scope.md` §Session capacity). Joining never widens the read surface, so it is always the cheaper direction; splitting is the one that costs. Batches must have the same lens, with one kind exception: a verify quality session may co-batch a file's `code:<file>` key with its unit's `design:<unit>:<file>` key — one reviewer collects the public facts and judges the unit design in a single pass, and the report carries the file's public block plus the design block — and that pairing extends across the files of one session, so one quality session may hold the code and design keys of several files. Any other kind mix, and any lens mix, stays rejected.

The coordinator finds related evidence (callers, callees, dependencies, tests) by repository search and supplies it explicitly. If a reviewer finds a missing evidence path, do not submit an incomplete verdict: add it to the open run with `specflowctl gate-extend` — accepted sessions keep their verdicts because the supplement broadens available read refs, not the required surface. Newly required evidence invalidates reuse even if existing content dependencies remain unchanged.

A public report contains `File: <key>`, `conclusion: FACTS`, `facts: <assessment>`, and potential finding blocks. Its dependency is the conclusion's own object — the reviewed file plus the applicable rules, whole-file — recorded by the tooling. The run's supplied evidence inputs stay part of the readable surface, but they never define the record's dependencies: neither an unrelated evidence edit nor a newly supplied evidence input re-runs the record, because verify freshness is bound to the conclusion's own record pins (see `framework/validation_cache.md` §Conclusion-bound verify freshness). The report carries no dependency-scope lines for it.

Design missions consume only the immutable `code:<file>` records for their assigned files, whether those records were executed, reused or carried — except a co-batched session, whose design judgments dispose the observations collected in the same report's code block. A public execution batch does not determine the design batch's inputs; observations and judgments for unassigned files are excluded. Execution dependencies still determine readiness. Mission generation and submission validation use the same per-file public records.

A design report contains `File: <key>`, its quality conclusion, `spec_requirements: <active assessment>`, one or more `Spec basis: <anchor>` lines, `gate_findings`, and exactly one `Observation disposition: <id> = retained|suppressed — <unit-specific evidence and reason>` for every public observation in the assigned files' records. Reports carry no dependency declarations beyond those anchors: the tooling records the run's whole input surface, pins the reviewed file whole-file, and pins the unit spec at exactly the anchors the report declared — a promise entry id, or the heading text of a `##` section or of a `###` or deeper narrative block, where heading text is the heading line without its leading `#` markers and surrounding space (the heading `### 3. Data Structures` is named `3. Data Structures`) — so an acceptance-item edit, or a narrative or promise edit the judgment never declared, re-runs nothing, while an edit to a declared anchor re-runs the judgment. An architecture judgment pins the whole unit main spec.

An architecture report uses `Unit: architecture:<unit>` and the existing six Dimension 8 assessments, quality conclusion and findings. It covers the entire unit rather than repeating architecture once per file.

## Immutable storage and task allocation

Accepted records live under `docs/specs/meta/validation/judgments/<protocol>/<kind>/<unit>/<subject>/<spec context>/<id>.json`. A record's own identity fields name its slot, so a reader that knows the key it is asking about opens that slot instead of searching the store; `<unit>` is `_` for a key that is not unit-bound, `<subject>` is the reviewed repository path (the digest of the item name for an acceptance item, `_` for a kind whose subject is its unit), and `<spec context>` is `_` when the record is not bound to one spec content. The tool derives their ids and digests from canonical record content, leaving a reference's slot locator out of the hashed bytes so a record's identity never depends on where its consumed records were filed. Records contain their kind and subject, coverage and read inputs, content dependencies, consumed record references, protocol fingerprint, verdict, findings or observations, dispositions, report and report digest, and source run. Accepted records cannot be replaced; rechecking creates a new record. Acceptance records also carry `spec_context`, a fingerprint of the normalized main spec and all appendices, using layer-independent own-spec names. Appendix ownership requires both the filename form and its frontmatter `unit`; an appendix of a distinct unit sharing the filename prefix is excluded. The same ownership inventory governs planning, context fingerprints, dependency normalization, fork and promote. Peer references resolved by name remain logical. Each unit, acceptance item and spec-context combination has an atomic current-record reference, `current`, inside that key's slot, advanced under the repository mutation lock. A missing, damaged, invalidated or stale current decision requires rechecking rather than selecting an older record. Cached records must satisfy both their original context's current decision and the currently bound stable context's decision, so publishing a new stable context cannot leave a conflicting historical pass valid. A different candidate spec context cannot overwrite or hide the stable context's current decision.

All required code inputs and published-rule inputs use exact whole-file content fingerprints in every judgment, including inputs without a separate report scope declaration. A report can select spec chapters and acceptance-item regions but cannot omit required code dependencies. Consumed records form a checked reference chain: missing, damaged, invalidated, stale or changed-protocol records invalidate their consumers.

The protocol fingerprint covers each gate's *judging* text — for verify, `unit_verify_checklist.md`, `shared_judgments.md`, `verification_scope.md`, `severity_policy.md` and `spec_writing_guide.md`; for unit validate, `unit_validate_checklist.md`, `verification_scope.md`, `severity_policy.md`, `spec_writing_guide.md` and `core/promise_model.md`; for rule validate, `rule_validate_checklist.md`, `verification_scope.md`, `severity_policy.md` and `spec_writing_guide.md` — and excludes the sections that describe how a run is planned, recorded, parsed or terminated. A framework update that only touches those sections therefore carries the recorded conclusions instead of invalidating them. A verify conclusion binds its standard per judgment record; a validate conclusion binds it in the cache (`framework/validation_cache.md` §Format → Standard binding).

`gate-plan` fixes necessary keys and input snapshots, recording executed, carried or reused sources. A coverage key added after planning — a validate review's named `Recheck:` key, or the design key a re-run public `code:<file>` key pulls — is stamped with the same execution source and shared task `gate-plan` gives the keys it plans. A persisted verify run's public `code:<file>` key therefore always carries a shared task or a bound public record; the strict loader rejects a run whose public key has neither, so the local-state sweep reclaims it. Shared public tasks under `meta/gate_runs/shared/` have one owner for the same file, evidence and protocol. A concurrent run consumes the accepted record or waits for the assigned run. An interrupted owner continues its task; when its run is replaced, a new run can claim that same pending task. The repository mutation lock serializes assignment, acceptance and publication. A task file lives only while some run references it: the local-state sweep (after `gate-plan`, a successful `promote`, or `specflowctl clean`) removes unreferenced task files. The durable result is the judgment record; a removed task file is recreated on demand.

Public judgments publish after independent report acceptance and their own snapshot checks. Unit judgments publish after accepted synthesis and complete snapshot checks. Their verdicts, logical statuses and findings are the finalized per-key decisions, including suppression, merging and failures introduced by synthesis. Design and architecture preserve their accepted three-state quality conclusions when no synthesis runs. When synthesis runs, it authors one final `Quality conclusion` per design and architecture key, including carried keys, with a reason. Logical pass/fail is stored separately and never converted into a quality conclusion. Changed carried or reused decisions also receive new records. Final-review evidence used for a changed decision joins its dependency closure. Input changes reject publication; old runs cannot replace a newer unit cache.

## Judgment and conclusion rules

Unit-private reasons never modify public observations. A nonblocking CANNOT_DETERMINE remains CANNOT_DETERMINE: a gate pass is not proof of alignment. `unacceptable` requires a gate-driving canonical P0/P1 finding; `acceptable` versus `needs_attention` remains the reviewer's assessment.

## Cache, delta and release

A unit's `verify_result.md` remains the complete gate entry, with schema 5 structured judgments, necessary check keys, immutable record ids/digests and source labels, plus the full human-readable report. Validate and rule caches keep their own roles and their own judgment schema; they bind no shared records.

Full verify repeats this unit's item, design and architecture judgments and may reuse public records. Delta re-executes changed dependencies and newly required coverage; repair additionally re-executes failures and explicit invalidations. Region dependencies still determine execution scope: an unchanged carried acceptance decision is published into the current spec context without repeating its review. Its previous context's current decision remains intact. Changing private design leaves valid public records reusable. Changing shared implementation invalidates every dependent record; the current run completes its required checks rather than verifying every other unit.

`gate-invalidate --judgment <id> --reason <evidence>` invalidates that immutable judgment and its consumers without deleting history. If newly reviewed evidence contradicts an accepted public fact, the coordinator must invalidate the contradicted record by id and cite that evidence before completing the run; its consumers cannot continue using the old result. `gate-invalidate --gate verify --unit <unit> --target <layer> --check <key>` also invalidates the contradicted immutable evidence before transitioning the unit cache and matching open runs, under the same repository lock. Acceptance-item ids are normalized to `item:<unit>:<item>` and select the current decision for the requested spec context even when the unit cache is absent. A different candidate context cannot invalidate the stable context merely because a forked cache still references its historical record. Public and unit-private quality keys select the records bound by the cache or matching open runs. All consumers reject invalidated evidence through the checked reference chain; history remains intact.

Fresh and promote derive required keys again from current declarations and stable associations, then check coverage, evidence, record digests, dependency closure, protocol and blocking findings. Missing or indeterminate state blocks release with the specific gap. Promote never starts reviews. Validate, rule publication and appendix requirements remain in force.

Fork and promote change only this unit's cache layer bindings and verify unchanged content. Removing a unit clears its current caches while preserving records used by other units. History cleanup is automatic and conservative: gate-finalize collects stale-protocol records that no current cache binding, no current decision of the deployed standard, and no open run reaches — including through the record-reference chain — and reports the reclaimed count and size; same-protocol superseded records are retained. A record's standard is the first component of its slot, so staleness comes from where a record is filed, never from its body, and an unreadable record filed under the current standard stays with the rest of that standard's history. A current-decision pointer counts only for the standard that filed it: no reader asks a retired standard for a decision, so that decision is collected too and its pointer is removed with it.
